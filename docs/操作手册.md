# OK8MP-M7 操作手册

## 1. 使用范围

本文用于复现已验证的 OK8MP Cortex-M7 固件启动和 CAN 功能测试。测试对象为 OK8MP P29 CAN1 接口、ESP32-S3 模拟 ECU 和 CAN 收发器模块，位速率为 500 kbit/s。

仓库中有两份已验证镜像。`firmware/nuttx-ok8mp-m7-openvela-baseline-tested.bin` 是原项目的基线镜像，用于系统启动、I2C 语音模块、uORB、安全网络和 AI Agent 基础功能验证，SHA-256 为 `02ffb2a7ad8ee94da7542b1ca41b369f566e047fe90051331de3078667f73a2d`。它不包含后续的 CAN 功能。

本手册的 CAN 测试使用 `firmware/nuttx-ok8mp-m7-can-uds-obd-tested.bin`，SHA-256 为 `1c3a6baaf3b4fb7ddf00fe9b5c345f6971704a77380eb6a8dd464f77a1a592a5`。

## 2. ESP32-S3 ECU 准备

进入 `app/ok8mp_m7_services/esp32_can_ecu`，使用 PlatformIO 编译和烧录。上传前关闭占用串口的监视程序，并将端口替换为实际设备名。

```bash
~/.platformio/penv/bin/pio run -t upload --upload-port /dev/cu.usbmodem11201
~/.platformio/penv/bin/pio device monitor --port /dev/cu.usbmodem11201 --baud 115200
```

ESP32 启动日志应显示 TWAI 工作在 500 kbit/s。串口输入 `t` 开始发送每秒一次的 `0x180` 状态帧，输入 `r` 停止周期发送但保留 CAN 应答；`p`、`j` 和 `x` 分别注入一次周期异常、序号跳变和异常诊断响应。

## 3. CAN 接线

| ESP32-S3 | CAN 收发器 | OK8MP P29 |
| --- | --- | --- |
| GPIO4 | RX | 无 |
| GPIO5 | TX | 无 |
| 3V3 | VCC | 无 |
| GND | GND | ISOGND |
| 无 | CANH | CAN1_H |
| 无 | CANL | CAN1_L |

CANH 与 CANL 使用同一对双绞线并保持同名相连。终端电阻应按照实际总线两端已有配置决定；本台架使用板载隔离 CAN 接口与收发器模块时，不额外并联电阻。

## 4. 传输镜像

在主机上核对镜像后上传到 A53 Linux 的 FAT 分区临时文件，再原子替换启动文件。将 IP 替换为开发板地址。

```bash
shasum -a 256 firmware/nuttx-ok8mp-m7-can-uds-obd-tested.bin

scp -O -oHostKeyAlgorithms=+ssh-rsa \
  firmware/nuttx-ok8mp-m7-can-uds-obd-tested.bin \
  root@<A53_IP>:/run/media/mmcblk2p1/nuttx.bin.new

ssh -oHostKeyAlgorithms=+ssh-rsa root@<A53_IP> \
  'mv /run/media/mmcblk2p1/nuttx.bin.new /run/media/mmcblk2p1/nuttx.bin && sync && sha256sum /run/media/mmcblk2p1/nuttx.bin'
```

远端 SHA-256 与本文第 1 节一致后再重启开发板。

## 5. 从 U-Boot 启动 M7

在 U-Boot 控制台执行：

```text
mmc dev 2
fatload mmc 2:1 0x80000000 nuttx.bin
md.l 0x80000000 2
bootaux 0x80000000
```

M7 串口设置为 115200 8N1。启动成功后显示：

```text
NuttShell (NSH)
nsh>
```

## 6. CAN 基础服务与链路检查

在 NSH 中执行：

```text
ls /dev/can0
can_service start
can_service recover
can_service status
can_service health
```

预期 `/dev/can0` 存在，`can_service` 显示 `running=1`，`recover=ok result=0`，健康结果中的控制器状态为 `error_active` 且错误计数为 0。

随后执行主动诊断：

```text
can_diagnostic
```

正常结果包含 `request id=0x700 data=A5 01 5A`、`response=0x708` 和 JSON 中的 `"ok":true`。ESP32 串口会记录 `RX id=0x700 dlc=3 data=A5 01 5A`。

## 7. 周期状态帧监测与故障注入

在 ESP32 串口输入 `t`，然后在 NSH 中执行：

```text
can_monitor start
can_monitor status
can_monitor health
```

预期监视器接收 `0x180`，状态为 `healthy`。可分别在 ESP32 侧输入 `p`、`j` 或 `r`，验证 M7 的 `period_error`、`counter_error` 和 `timeout` 检测。恢复 `t` 后，状态应重新变为 `healthy`。

物理断开 CAN 双绞线后执行 `can_diagnostic`，预期在约 1 秒后返回 `"state":"timeout"`；重新接线后执行 `can_service recover` 和 `can_diagnostic`，应恢复为 `"ok":true`。

## 8. ISO-TP、UDS 与 OBD-II 验收

```text
can_ecu isotp-test
can_ecu uds session extended
can_ecu uds tester-present
can_ecu status
can_ecu dtc
can_ecu set overtemp
can_ecu status
can_ecu dtc
can_ecu set normal
can_ecu dtc clear
can_ecu set low_voltage
can_ecu status
can_ecu dtc
can_ecu obd supported
can_ecu obd coolant
can_ecu obd voltage
can_ecu obd dtc
can_ecu obd vin
```

`isotp-test` 应确认 32 字节 UDS RoutineControl 的多帧请求和响应。正常状态下，`status` 读取 `normal`、60 ℃ 和 12600 mV；发动机过热状态对应 DTC `P0217`，低电压状态对应 DTC `P0562`。恢复正常并执行 `can_ecu dtc clear` 后，UDS 与 OBD-II 的故障码查询应为空。

完整验收记录见 `test-results/nsh-can/实测记录.md`。
